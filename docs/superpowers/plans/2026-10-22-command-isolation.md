# App-engine command isolation implementation plan

**Status:** In progress under Beads `atrium-slrr3.3`. The approved production
security design is in `docs/superpowers/specs/2026-10-22-production-security-design.md`.

## Boundary and proof

The app-engine daemon keeps its present `appengine` account, SMTP path, and
loopback API. Managed app commands run as distinct transient Unix UIDs in
systemd units. Each unit sees its own app source at `/workspace`, data at
`/app-data`, and build directory at `/app-build`; its `/home` and the broker
socket are hidden. The unit shares the host network namespace so an app can
bind its normal `127.0.0.1:$PORT`, but systemd cgroup policy denies non-loopback
IP traffic. Local services still require their own authentication. A separate
bounded package-fetch operation is required for dependency installs that need
Internet access.

The VPS probe on 2026-10-22 showed `DynamicUser=yes`, `Group=appengine`, and
`UMask=0002` create a different UID with appengine-group writable outputs in a
scoped bind. `IPAddressDeny=any` plus `IPAddressAllow=localhost` denied
`1.1.1.1:443` and allowed `127.0.0.1:8770`. This is a substrate check, not a
runner acceptance test.

## Components

1. `app_engine/isolated_units.py` builds transient-unit arguments from a
   root-owned allowlist of app and state roots. It rejects path escapes,
   symlinked roots, mismatched `app.json` IDs, invalid unit names, and paths
   that systemd might interpret as property syntax. No app argv or secret
   environment value appears in those arguments. Unit names are generated by
   the broker and never accepted from the engine client.
2. `app_engine/isolated_exec.py` is the unit's fixed executable. It reads one
   bounded JSON plan from standard input, checks argv/environment size and
   syntax, maps the working directory into the three bound roots, closes
   standard input, and `execve`s the exact executable without a shell.
3. A root-owned socket-activated broker listens at
   `/run/app-engine-runner.sock` with socket owner `appengine` and mode
   `0600`. It also checks `SO_PEERCRED` for the configured engine UID. The
   broker validates every request against its own allowlist and manifest,
   creates a random transient-unit name, passes the command plan on the
   unit's standard input, and streams bounded stdout/stderr frames back to
   the client. Each transient unit `BindsTo` its socket-activated broker
   instance, so a broker crash also stops the app unit. Disconnect, timeout,
   and stop requests stop the exact unit;
   a stale unit is reaped on broker startup. The broker never executes an
   arbitrary client-supplied host command.
4. An engine-side runner client exposes `spawn`, `wait`, `communicate`, and
   `stop` to `ProcessLifecycleManager`. `enforce` selects this runner and
   refuses a missing or unhealthy broker. `audit` and `legacy` retain their
   current behavior. Preparation and start use the same runner; the health
   check still reaches the app's host-loopback port. The manager translates
   app-root, data, build, cwd, and executable paths to unit-visible paths.
5. The package-fetch lane accepts a lockfile-backed request with a configured
   HTTPS registry origin and digest checks. It deposits packages in a scoped
   cache outside the app unit; install/build commands then run offline inside
   the unit. A command that needs network without a verified cache fails
   closed. No generic outbound proxy is granted to an app command.

## Verification sequence

First run focused local tests for path validation, broker peer authentication,
protocol limits, lifecycle stop/timeout behavior, and no host subprocess
fallback. Then exercise the Linux runner with a synthetic managed app: a
controlled external TCP receiver must see no connection, an app must serve its
loopback health route, and distinct launches must have distinct Unix UIDs.
Check that the app cannot read the engine's private home or broker socket.

Before production enforce, migrate only the pilot app's state and build
directories to appengine-group read/write permissions, preserving a backup.
The pilot is `cyberpunk-tcg`, whose live manifest has a process `start` step
and no install/build steps. Its live price-refresh path does fetch TCGCSV over
HTTPS and writes `data/` inside the app source tree, so applying egress deny
without a fixed-origin fetch operation and a scoped writable data mapping would
break a production feature. The multiplayer room service runs as a child on
loopback and must remain in the same unit/cgroup. Its start command resolves
`uv` through `/usr/local/bin/uv` into the hidden engine home, so a visible
trusted toolchain or a reviewed manifest change is also required. Add these compatibility gates
before using the pilot. Obtain owner approval for its exact launch plan;
do not synthesize or auto-approve that authority token. After the approved
launch, verify the app UI, data persistence, crash/stop cleanup, engine SMTP,
store catalog, both mTLS directions, and rejected non-loopback egress. The
production inventory also has `package-tracker`; it needs Playwright, carrier
API and merchant-page access, and Atrium mail access, so global enforce must
wait for that separate compatibility path. Keep
`APP_ENGINE_PROCESS_ISOLATION=audit` and, after the pilot's exact launch plan
is owner-approved, use `APP_ENGINE_ISOLATED_APP_IDS=cyberpunk-tcg` to isolate
only that app. The production flip and rollback procedure must be documented
with the reviewed PR and tested on the VPS before calling isolation complete.
